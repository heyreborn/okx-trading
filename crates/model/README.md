# model

Owns stable cross-package contract primitives. `src/lib.rs` exports the initial schema marker and `identity`, `units`, and `facts` modules. There is no trading policy, persistence or OKX network code here.

`identity` validates each namespace-specific ID at construction and JSON decoding. The wire form is a string, preserving case and bytes; IDs are nonempty, ASCII, at most 128 bytes, and contain letters, digits, `-`, `_`, `.`, or `:` after an alphanumeric first character. Different ID types cannot be passed interchangeably. A collection owner must still reject duplicate IDs and check cross-reference integrity. Validation is pure: no I/O, state, retries, or transaction boundary. It does not check account permission, OKX existence, or environment. The schema marker does not validate or migrate envelopes.

Python reference: `../okx-trading-py/src/okx_trading/domain/contracts.py` and `tests/test_contracts.py` encode typed contract identifiers and reject incompatible envelope versions. Rust intentionally uses separate ID types and tests JSON round trips, invalid inputs, and duplicate detection in `identity.rs`. Schema-version checks remain the owning message contract's responsibility; wire compatibility beyond string identity and database round trips remain unverified.

`units` parses only plain decimal strings into BigDecimal, rejects float JSON, non-finite text, exponent notation and values outside 20 integer/18 fractional digits, and serializes exact plain decimal text. `Money` carries currency and checks it on addition; `Price` carries base/quote denomination; spot `BaseQuantity` and SWAP `Contracts` are separate product-bound types. Their constructors and JSON decoders reject negative quantities. `Ratio` accepts only 0 through 1. Source and receipt UTC Unix milliseconds are separate types. `floor_to_step` rounds nonnegative values down; planning must apply current OKX tick/lot facts and recheck all limits afterward. There are no asynchronous tasks or transactions here. Python's contract tests reject decimal floats and wrong quantity units; Rust's `units.rs` tests enforce exact parsing, mismatched currency, boundary rounding, overflow and invalid JSON. The 38,18 domain is a Rust contract choice for future PG NUMERIC columns; a real PostgreSQL round trip and real product extrema remain unverified.

`facts` owns schema-one envelopes for already-normalized market events, absolute strategy targets, account positions, order observations and individual fills. JSON decoding rejects unknown fields, versions, enum values and cross-field unit or position-mode conflicts. Order cumulative fills and individual fill quantities keep their SPOT-base or SWAP-contract variant and product identity. `Availability` distinguishes missing, fresh, stale and unresolved states; a zero target is distinct from `NoSignal` and `Unavailable`. `FactEnvelope::new` is the pure validation boundary; the exchange adapter must validate raw input first. Later modules own event-ID construction, freshness thresholds, order transitions, account trust and transaction boundaries. Python's `domain/contracts.py` and `tests/test_contracts.py` provide behavior evidence for strict version/unit validation and dual-side positions; Rust's `facts.rs` tests assert independent invariants rather than Python output equality. Version-zero/two payloads are explicitly rejected because no previous Rust fact schema exists to migrate. Future schema evolution needs a separate migration and replay test. Actual remote facts and cross-process delivery remain unverified.

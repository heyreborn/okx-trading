# integration-tests

Owns cross-package and isolated service acceptance tests. `src/lib.rs` documents the package boundary. `tests/connectivity.rs` invokes service clients inside an explicitly named Compose project to verify PostgreSQL, Kafka and signed S3 PUT/GET. `tests/stage1_catalog.rs` checks the model/config/instrument contract offline and contains an ignored, explicitly gated OKX demo Read-only directory check. `tests/stage1_numeric_pg.rs` is an ignored real PostgreSQL `NUMERIC(38,18)` round-trip and overflow test. `fixtures/connectivity-v1.txt` contains only a public marker; no account, market, or credential data is stored here.

The connectivity test requires `OKX_TEST_COMPOSE_PROJECT=okx-stage0-test-<suffix>` and refuses other project names. Start `deploy/compose/compose.yaml` under that project and run the `kafka-init` profile before `cargo test -p integration-tests --test connectivity`. The numeric test instead requires its own `okx-stage1-test-<suffix>` project with only healthy PostgreSQL and runs with `OKX_TEST_COMPOSE_PROJECT=... cargo test -p integration-tests --test stage1_numeric_pg -- --ignored`. It makes no persistent table. These tests use Docker CLI and container clients; Rust SQLx, rdkafka and object-store adapters do not exist yet. The connectivity test writes a repeatable object key and has no transaction or message offset ownership.

`cargo test -p integration-tests --test stage1_catalog` runs the offline multi-product, multi-instance, mode, fee and freshness assertions. Its second test is ignored by default and must be run only with explicit authorization for a demo account whose credential has Read permission. Set `OKX_STAGE1_DEMO_READ_ONLY=1`, `OKX_STAGE1_DEMO_REGION=global` or `us`, and `OKX_STAGE1_DEMO_KEY_FILE`, `OKX_STAGE1_DEMO_SECRET_FILE`, `OKX_STAGE1_DEMO_PASSPHRASE_FILE` to protected secret-file paths, then run `cargo test -p integration-tests --test stage1_catalog authorized_demo_catalog_acceptance -- --ignored`. It uses fixed demo endpoints and GET methods only, prints no credential or full response, and compares the example's BTC-USDT SPOT/BTC-USDT-SWAP bindings to the observed account. A different account mode or unavailable product fails acceptance; adapt the reviewed config and test before a new run. The test owns no persistent state, retry or order submission.

See [DEV-004, DEV-008 and DEV-013](../docs/development-roadmap.md), [stage-one acceptance report](../docs/stage1-acceptance.md), [testing strategy](../docs/testing-strategy.md), and [deployment](../docs/compose-deployment.md). Python's strict contract and catalog selection tests informed the offline boundaries, but all tests are Rust and assert this repository's own contract. Real demo acceptance, application role wiring, SQLx and multi-node recovery remain unverified.

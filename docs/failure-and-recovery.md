# 故障边界与恢复

状态：设计草案。原则是先确定受影响的账户、产品或数据链路，再暂停相应新开仓；恢复必须有可验证事实，而不是仅因连接重新建立。订单事实以 OKX 为准，本地策略归属和预留以 PostgreSQL 为准。详细状态契约见 [契约与不变量](contracts-and-invariants.md)。

## 暂停粒度

| 故障 | 立即处理 | 恢复条件 |
| --- | --- | --- |
| 单产品公共行情断线、盘口缺口或价格过期 | 标记该产品相应 feed 不可信；停止依赖该 feed 的新开仓目标。 | 重订阅、所需快照/预热完成，时间与序列重新连续。 |
| 跨产品策略任一输入不可信 | 仅暂停该策略的新目标及其候选。 | 所有声明输入重新满足对齐与新鲜度要求。 |
| Kafka 发布失败或采集队列满 | 采集停止声称事件连续；受影响 feed 暂停，记录缺口。 | Broker 确认恢复，重新建立 feed 可信状态和消费进度。 |
| 采集所有权切换、租约未知或旧代次事件迟到 | 受影响 feed 停止可信输出；隔离旧代次迟到记录并保留审计。 | 新代次重新订阅，快照/预热与序列连续性核验通过；不能仅凭租约切换恢复。 |
| 同 ID 异业务载荷或身份规则版本不兼容 | 隔离冲突，停止相关消费者进度与交易输入。 | 用原始记录、schema/身份版本和来源事实核查，明确迁移或重新建流。 |
| 观察消费者重平衡、重复或迟到事件 | 停止该分区决策输出，保留已确认的处理检查点。 | 从安全检查点重放并去重；超出重排窗口时明确跳过和标记不可信。 |
| 策略实例所有权丢失、状态版本不兼容或旧目标迟到 | 暂停该实例的新目标与其受影响产品的新开仓；旧代次消息隔离。 | 新代次从已提交状态/目标检查点重放，确认代码、参数、绑定及输入水位兼容。 |
| 目标过期、无信号或组合冲突 | 不将无信号解释为归零，不使用过期目标新批准；冲突批次拒绝新增开仓。 | 有效的新目标、可信实例库存及明确组合政策通过校验；已有订单继续按远端事实恢复。 |
| 对象存储/归档不可用 | 归档消费者不确认尚未持久化的事件；报警并监测 Kafka 剩余保留窗口。 | 对象与清单可读、积压追平且校验通过；接近日志保留上限时停止依赖审计归档的交易准入。 |
| PG 不可用或主从切换 | 所有账户停止新批准和 outbox 领取；采集节点停止新发布并使受影响 feed 失信，执行者保留未知状态。 | 新主库已确定，采集发布权代次、feed 连续性、账户所有权、未终结订单、预留与远端事实分别核对。 |
| 账户余额/仓位快照过期、模式变化或外部交易 | 暂停该账户新开仓；不以旧策略归属推断远端仓位。 | 重新取账户、仓位、活动订单及成交，处理差异并标记信任。 |
| 私有 WS 断开或回报序列不可信 | 暂停账户新开仓和不确定订单的后续提交。 | 重新登录订阅，REST 核对所有未终结订单及成交，恢复信任门禁。 |
| 下单 POST 超时、连接断开或响应无法解析 | 原意图进入 `unknown`，保留预留；禁止生成替代 client ID。 | 使用原 `clOrdId` 查询订单与成交，得到可信终态或活动状态。 |
| 撤单请求结果未知 | 保留订单为活动或未知，不释放预留，也不假定零成交。 | 查询远端订单和逐笔成交，确认最终状态。 |
| 成交、费用或资金费不一致 | 暂停相关产品或账户新开仓，保留原始事实与差异。 | 远端账单/成交与本地幂等账本核平，必要时人工处理外部归属。 |
| trader 进程失联或所有权过期 | 待命副本暂停提交，获取新代次后先对账。 | 旧代次不能再批准；在途 HTTP、远端订单和预留均核清后开放新单。 |
| 告警渠道故障 | 将告警保持待投递并暴露渠道健康失败。 | 投递与确认位点恢复；关键交易故障仍可由独立监控发现。 |

暂停粒度由事实依赖决定：产品行情故障不必阻断健康产品；账户、私有流、PG 或执行权失真会影响整个账户。是否允许已有风险降低订单由可信远端仓位、交易规则和专门政策判断，不能自动放行。

## 接管协议

1. 待命 `trader` 通过 PostgreSQL 事务领取账户所有权代次；一个代次只授权批准事务。领取失败的副本保持只读。
2. 新执行者先保持账户暂停，读取本地未终结订单、预留和 outbox，再从 OKX 查询账户配置、仓位、活动订单与逐笔成交。
3. 对每个 `reserved`/`submitting`/`unknown` 意图按稳定 `clOrdId`、已知 `ordId`、产品及成交记录联合核对。OKX 不保证 `clOrdId` 历史永久唯一；确认远端不存在并满足交易所身份规则前，不重新提交。无法判定时持续暂停并告警。
4. 应用单调订单状态与幂等成交归因，核对余额、仓位、费用、预留和策略库存；差异不能自动用本地快照覆盖远端。
5. 私有流重新就绪、市场与账户事实新鲜、所有权代次仍有效后，才可解除相应门禁。恢复动作和依据写入审计记录。

数据库代次只能阻止旧执行者的新**数据库批准**，不能撤销已经发出的 OKX HTTP 请求，也不能把代次交给交易所强制执行。因此系统不承诺跨 OKX 与 PostgreSQL 的严格 exactly-once 提交。遇到旧执行者恢复与新执行者接管竞争时，优先暂停、查询和核对；以稳定订单身份、远端事实和故障测试限制重复下单风险。

## 消息与归档恢复

Kafka 生产者只有收到 Broker 确认才记录发布成功。发布确认未知且没有持久采集 ID 时，来源又没有稳定身份的重收事件无法可靠去重，相关 feed 必须标记不可信；不能用新 ID 伪装为已恢复连续。消费者提交位点前需完成其拥有的持久动作：归档者先写不可变 Parquet 对象并发布可验证清单；观察者先保存处理检查点及对应去重水位。提交位点失败会重放，故事件、清单和检查点必须幂等。跨 Kafka、PG 和对象存储没有共同事务，不能把三者的“已提交”简化成一个布尔值。

恢复 Kafka 数据时先检查最早可读位点、本地检查点与去重状态保留水位。日志保留期导致缺口或去重状态无法覆盖重放范围时不得静默从最新位点继续交易；需要用归档和可核验事件索引补足，或者将相关 feed 标为不可信并重新预热。归档中同版本相同事件 ID 但业务载荷不同属于冲突，不做“最后写入胜出”。WS/REST 补数若未验证同源身份与粒度，不覆盖原事件或抹去缺口。详细边界见 [行情事件身份与采集接管](market-event-identity.md)。

## 运维演练要求

每种故障演练都记录触发时间、受影响范围、暂停原因、未终结订单、远端核对结果、恢复时间与数据缺口。备份恢复演练使用隔离环境；恢复 PG 后重新从 OKX 核对账户和订单，备份中的“可信”状态不继承。配置发布和回滚不得自动修改交易所账户模式或杠杆。任何自动交易门禁的重新开放都要求对应故障场景通过 [测试策略](testing-strategy.md)。

# 实施协议与待验证细节

状态：编码前设计草案。本文将 [架构](architecture.md)、[领域不变量](contracts-and-invariants.md) 和 [故障恢复](failure-and-recovery.md) 转为可实现的流程；相应组件的取舍见 [技术决策](technology-decisions.md#与实施协议的对应选择)。标为“待冻结”的数值必须先用官方 OKX 文档、模拟盘只读事实及测试确定；不得把示例阈值写成交易所规则。接口核对从 [OKX 官方 API 依据](okx-api-reference.md) 开始。

## 完成一项实现设计的标准

每个跨进程或涉及订单的用例，在编码前记录：输入及其来源/时效、输出、状态拥有者、事务边界、可取消点、超时后状态、重试条件、幂等键、暂停范围、观测指标和测试。不能回答其中一项时，先做最小协议原型或保持只读。设计结论要落到所属 module 的类型、数据库约束或测试，不能只停留在文字约定。

## 异步任务与资源所有权

| 进程 | 长期任务 | 队列与确认边界 | 停止时的动作 |
| --- | --- | --- | --- |
| `ingest` | feed 发布权续租、WS 连接/重连、订阅、事件校验、Kafka 发布 | 每 feed 单活发布且事件带所有权代次；WS reader 到发布者使用有界队列；只有 Broker 确认才算已发布。租约未知、队列溢出或来源断线使对应 feed 失信。 | 停止接收和新发布，等待有限时间内的 Broker 确认；未确认区间记录缺口并使 feed 重新预热。 |
| `archive-worker` | Kafka 消费、批量编码、对象发布、清单登记 | Parquet 对象和可验证清单持久化后才提交消费进度；重复消息按事件身份处理。 | 结束当前可提交批次；未完成对象不发布为可读清单，位点留给重放。 |
| `observe` | Kafka 消费、重排、实例所有权、目标生成、检查点 | 每实例有单活代次；状态/输入水位/目标 outbox 同 PG 事务，之后确认 Kafka 位点；缓冲有事件数与字节上限。 | 分区撤销时停止该实例新目标，提交可恢复检查点；未完成区间由新代次重放。 |
| `trader` | 账户所有权、私有 WS、REST 核对、outbox、告警 | 私有回报和远端查询优先于新开仓；每账户有串行批准边界。 | 撤销新批准；对已提交但未确认的外部请求保持 `unknown`，交接给下一个执行者核对。 |

所有任务由进程级 supervisor 持有 `JoinHandle`，记录启动、退出和异常；关键任务意外退出立即改变 readiness 与对应交易门禁。取消令牌只通知停止，不假定 `Future` 被 drop 就撤销了数据库事务或远端请求。对 `select!` 中的发送/接收、数据库查询和 HTTP 请求逐一审查取消安全性；有副作用的工作以持久状态交接。阻塞 Parquet 编码、压缩或 CPU 密集计算不能长期占用 Tokio worker；专用受限执行池与内存预算由压测确定。

## 超时、时钟与背压

- 网络连接、单次请求、整段用例和优雅停机分别设超时预算；一个内层重试不能超过外层截止时间。OKX 下单 POST 不使用通用自动重试。读取接口只在明确可重试且仍满足事实新鲜度时重试。
- 签名时间使用经过校准的 UTC 时钟；持续监测与 OKX 系统时间的偏差。任务持续时间、重试间隔和租约等待使用单调时钟。交易所时间、接收时间、Kafka 时间和本机处理时间分别保留，禁止互相覆盖。
- 每条链路同时限制队列条数、总字节数、并发请求数和最大事件年龄。满队列时上游停止读取或显式标记缺口；不能无声丢弃后继续输出可信信号。
- OKX REST 按接口、用户和产品适用范围限速；私有恢复查询、撤单与新开仓分配独立预算。容量不足时优先恢复和风险控制，并暂停新开仓，不靠无限排队等待过期请求。
- Kafka 消费重平衡时暂停对应分区输出，清理或持久化缓冲，再从可验证位点重放。跨产品策略必须按声明的输入时间窗口聚合，不能按 worker 到达顺序产生目标；实例所有权代次、状态/目标原子检查点见 [策略目标与实例执行协议](strategy-target-and-execution.md)。

队列长度、事件字节上限、年龄阈值、请求超时和重排窗口均为**待冻结**参数。冻结依据是多节点突发试验、OKX 限速和策略所需新鲜度；配置必须有上下限校验和运行指标。

各阶段预算、排队与计算成本、饱和行为及容量验收按 [性能与容量设计](performance-and-capacity.md) 测量。任何批处理或增量计算优化都需保持本协议的确认、精度、可信状态和恢复边界。

## 精度协议

| 类型 | 必须携带 | 计算和检查 |
| --- | --- | --- |
| `Money` / `Fee` | 币种、十进制值 | 不同币种不得直接相加；费用保留符号、实际扣费币种和来源。 |
| `Price` | 报价币种/基础币、产品规格版本 | 限价按当前 tick 及价格限制校验，规格变化使计划失效。 |
| `BaseQuantity` / `Contracts` | 产品、单位、十进制值 | 现货基础币与合约张数不得隐式转换；数量按 lot 取整后重检最低量。 |
| `Notional` / `Margin` | 币种、估值时间、换算来源 | 合约面值、标记价、杠杆和费用各自有来源版本；双侧毛额不相抵。 |
| `Ratio` | 无量纲值、政策版本 | 限定范围及小数精度；不能把 bps 当比例使用。 |

解析外部十进制字符串后先检查范围和精度，再计算；中间乘除限制有效位数和结果规模。除法必须选择业务定义的舍入模式。订单价格和数量按 OKX 当前规格取整，随后以**已取整订单**重新评估名义金额、费用、滑点、保证金和所有预算。金额不符合数据库列范围、无法精确表达或将突破政策时拒绝计划。`model::units` 首版将跨包数值冻结为不超过 20 位整数、18 位小数的十进制字符串，对应未来 `NUMERIC(38,18)`；不接受指数形式或隐式舍入。数据库列迁移实施前仍须以真实 PostgreSQL 进行往返、极值、步长边界和多笔分摊余数测试；余数分配规则必须确定且守恒。除法和规划取整表随相应领域用例冻结，不能沿用通用默认模式。

## 账户批准、提交与接管

`trader_usecases` 内将批准、发送、回报入账和接管/对账实现为独立用例。目标交付使用 `observe_usecases` 在 PG 同事务写入的目标 outbox；投递可重复，批准用例先按 `target_id` 去重，并检查实例代次、绑定版本和有效期。批准用例是本地订单批准的唯一编排者：在事务外用可信快照调用 `portfolio` 与 `planning` 预计算；进入账户锁后重读/复核事实、目标有效期、执行权代次、配置与规格版本，按最新事实重算受变化影响的结果并调用 `risk`。若所需远端事实无法在事务中读取，以已核验快照及其版本/年龄作门禁；版本不符或过期则拒绝，不在锁内调用 OKX。`persistence` 提供锁、查询、约束和提交能力，不生成额外批准或改写风险结果。

```text
observe_usecases：状态/目标/检查点/目标 outbox 同 PG 事务 -> 确认 Kafka 位点
  -> 目标 outbox 可重投递交付；trader_usecases::approval 去重并核对代次与有效期
  -> portfolio + planning 在锁外用可信快照预计算
  -> trader_usecases::approval 开始 PG 事务、锁账户、复核目标/事实/版本
  -> 必要时重算组合与候选；risk 用锁内事实计算额度和预留
  -> persistence 同事务提交决策/意图/预留/订单 outbox/份额/审计
  -> trader_usecases::dispatch 领取订单 outbox、复核发送权，经 okx-client 请求 OKX
  -> HTTP 响应、私有 WS 和 REST 查询分别形成有类型远端事实
  -> 正常事实由 trader_usecases::settlement 核验；未知结果由 reconciliation
     使用原 clOrdId 查询，核清后交 settlement，不能盲目重发
  -> settlement 用 order::state + accounting 计算状态、成交及归属
  -> persistence 同事务入账、调整预留和审计，重新核验账户事实
```

事务中不等待 OKX 网络调用。首版以账户行锁序列化账户批准，并由数据库唯一约束保护决策、订单身份、成交和 outbox；若跨账户共享风险以后成为需求，再设计独立锁顺序和共同额度边界。正常私有回报无需等待未知结果核对用例；HTTP 接受只证明请求状态，不证明成交。`order::state` 只判定状态转换，`accounting` 只计算逐笔成交、费用与归属；回报入账用例在账户锁下核对本地订单和累计成交，将两者结果同事务保存，不让适配器凭网络回报直接修改账本。事务隔离级别、索引与死锁重试要在真实 PostgreSQL 并发测试中确认；不能只依赖进程内 mutex。

outbox 领取保存 owner、代次、租约和尝试状态。领取与确认是两次独立事务；任何返回前崩溃都可能留下 `unknown`。发送前的代次检查降低旧执行者提交概率，但不能阻止已在网络中的请求，所以不承诺 OKX 端 exactly-once。接管者先暂停账户、查询所有未终结订单、成交和仓位，按 `clOrdId`、远端 `ordId`、产品及时间联合核对；查询不足以证明不存在时保持暂停。`clOrdId` 本地永不复用，不能把 OKX 对未完成订单的唯一性当成永久幂等保证。

撤单接受不等于撤单终态；部分成交与撤单可交错。预留释放依据远端终态和已核验累计成交，逐笔费用依据成交/账单。一个决策产生多笔 SPOT/SWAP 或双侧订单时，OKX 不提供跨订单原子提交：每条意图独立记录、恢复，单腿失败不得伪造整组成功。

## 安全与权限

- `ingest`、`archive-worker`、`observe` 不持有交易密钥；只需公共行情的任务不加载账户密钥。`trader` 的私有读取与交易权限按环境及进程角色最小化，密钥由部署环境注入并支持轮换。
- 初版强制模拟盘配置：REST/WS 端点、密钥环境和 `x-simulated-trading` 同时校验；未知域名、代理重定向、地区不匹配或配置混用时启动失败。HTTP 客户端禁止把签名头、请求体中的密钥或完整账户数据写入日志。
- 对外部 JSON、WS 消息和配置做大小、深度、字段与枚举校验；无法识别的交易所状态或业务码不能默认当成功。结构日志只记录必要 ID、状态和脱敏摘要。
- 内部服务与数据库/队列使用 TLS、独立凭据和网络权限；管理、探针与配置发布需要与常驻交易进程分开的权限。初版没有实盘开关。
- 审计记录需要写入来源、操作者或自动决策 ID、版本、时间和结果；修改策略预算/风险政策不能静默覆盖在途决策。备份中的密钥、账本及原始响应按部署的访问与保留政策管理。

## 配置发布、数据演进与运维

一个决策引用冻结的策略目标、实例状态、绑定、产品规格、风险政策及输入版本。配置发布先通过静态校验、内容摘要核对与只读对比，再滚动部署观察节点；账户执行者在安全边界切换版本。旧代次、过期目标或版本分歧暂停受影响的新开仓。环境变量只调整部署接线，不改变业务配置或交易门禁。回滚不能改变已提交意图的解释，也不能凭旧配置重发订单。需要变更仓位模式或杠杆时，由账户持有人另行操作；程序只检测并暂停核对。具体来源和职责见 [配置、环境与观测规范](configuration-and-observability.md)。

消息、Parquet 和 PG schema 独立版本化。消费者遇到未知必需版本、冲突事件 ID 或毒性消息时隔离、告警并停止相关进度，不能无限重试或跳过后继续交易。归档对象不可变；清单、Kafka 位点与 PG 检查点的恢复关系需有演练。保留期、备份频率、恢复时间目标和数据丢失目标由部署设计确定，并与 Kafka 最短保留窗口、OKX 历史查询窗口共同验证。

readiness 反映角色所需依赖和可信度，liveness 只反映进程是否需要重启；不能用“HTTP 健康接口返回 200”解除交易暂停。指标至少包含每 feed 新鲜度与缺口、Kafka lag、队列高水位、PG 批准时延、outbox 未知数、账户信任与暂停原因、私有流重连及告警投递失败。指标标签控制基数；订单/决策 ID 留在结构日志和审计中。关键交易审计事实与账本同事务持久化，日志丢失不得影响恢复。告警渠道自身失效须由独立监控发现。

## 必须完成的设计核查

| 核查对象 | 证明方式 | 未通过时 |
| --- | --- | --- |
| Tokio 取消、背压和停机 | 可控任务测试 + 多节点突发，检查丢弃、延迟和资源上限 | 不运行可信观察或交易。 |
| 小数与数据库精度 | 性质测试、极值、PG 往返和真实产品规格样本 | 不生成可提交意图。 |
| 账户并发与执行者接管 | 双执行者真实 PG 竞争、网络分区、旧进程恢复 | 交易者保持只读。 |
| 下单/撤单未知结果 | 假 OKX 故障矩阵 + 模拟盘对账证据 | 自动提交关闭。 |
| 多产品多策略共享额度/归属 | 同账户 SPOT/SWAP 并发、双向侧别、部分成交分摊 | 对应产品/模式不开自动交易。 |
| 策略目标与实例接管 | 零/无信号/过期、反向冲突、预算不足、状态迁移、双观察者竞争 | 目标保持只读，不批准新订单。 |
| 配置发布与灾难恢复 | 冻结版本回放、数据库恢复、Kafka 缺口及对象清单核验 | 保持暂停，人工核对。 |

这些核查属于 [测试与验收策略](testing-strategy.md) 的实施证据。每个未通过项要保留失败输入、系统状态和原因；不得仅调大超时、队列或精度上限使测试表面通过。

实施时核对的底层语义：[Tokio `select!` 取消安全性](https://docs.rs/tokio/latest/tokio/macro.select.html)、[Tokio 有界 `mpsc`](https://docs.rs/tokio/latest/tokio/sync/mpsc/)、[PostgreSQL 显式行锁](https://www.postgresql.org/docs/current/explicit-locking.html)、[SQLx 事务](https://docs.rs/sqlx/latest/sqlx/struct.Transaction.html)。这些资料解释库和数据库行为；OKX 请求与回报仍以 [OKX 官方 API 依据](okx-api-reference.md)逐项核对。

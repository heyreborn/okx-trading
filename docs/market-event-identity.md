# 行情事件身份与采集接管

状态：设计草案。本文定义采集、Kafka、归档、观察和回放共同遵守的事件身份。逐频道的 OKX 字段语义仍须在实现前依据 [官方 API 索引](okx-api-reference.md#产品目录与行情)及模拟盘/只读样本核对；下表是判定规则，不预设某个字段在所有频道全局唯一。基础契约见 [契约与不变量](contracts-and-invariants.md#行情事件身份)。

## 两种身份与消息信封

每条规范化业务事件有非空 `event_id`；同一条事件被 Kafka 重投递、Parquet 归档或历史回放时保留它。原始 WS/REST 记录另有 `capture_id`，用于追溯连接、帧和解析结果。一个原始帧可生成多条业务事件，其 `event_id` 各不相同，并共同引用原始 `capture_id`。`capture_id` 不能代替交易所事件身份。

消息信封至少带 `event_id`、`identity_rule_version`、`schema_version`、`source`（交易所、模拟盘环境、WS/REST、频道）、内部 `product_id`、OKX `inst_id`、产品映射版本、事件种类、业务来源键或采集 ID、采集所有权代次、来源会话、交易所时间（若有）、接收时间、序列字段（若有）和原始记录引用。Kafka topic/partition/offset、重试次数和归档对象位置是后续传输元数据；不进入业务身份。产品映射规则见 [产品与策略身份及绑定](product-strategy-model.md)；派生事件另外保存父事件 ID 与转换版本，不能伪装成交易所原始事件。

身份规则在同一命名空间内确定性编码，编码格式和哈希算法随 `identity_rule_version` 冻结。优先使用经官方文档与样本证明稳定且唯一的来源键；来源键不足时，在**首次采集**时生成采集 ID，并在同一条记录的所有重试和持久副本中保留。来源键缺失时，不用价格、数量、时间戳或载荷哈希猜测两个连接上的推送相同。若发布确认结果未知且进程崩溃，本地又没有持久保存采集 ID，则重收事件无法沿用原 ID；这段区间标记为无法证明无重复/无缺口，并按 feed 恢复规则处理。若要求崩溃后仍沿用该 ID，必须在发布前持久保存采集记录及 ID，并验证恢复协议。

| 事件类别 | 实现前必须核对 | 允许的身份判断 |
| --- | --- | --- |
| 逐笔与聚合成交 | `trades-all`、`trades` 的交易 ID、聚合边界、频道与产品内唯一性及历史 REST 对应关系 | 逐笔和聚合事件分开命名空间；只有确认相同粒度与稳定来源键后才可跨连接或跨 WS/REST 认定相同事件。 |
| 盘口快照与增量 | `books`、`books5`、`bbo-tbt` 的快照/更新类型、序列作用域、重连重置及同序列多消息情况 | 序列只在被证实的作用域内作身份候选；无足够来源键时用采集 ID。身份去重不能代替 `seqId`/`prevSeqId` 连续性。 |
| K 线 | 周期、开始时间、未收盘更新、`confirm` 与 REST 历史版本 | 同一周期的多次更新是不同观察事实；周期键不是事件 ID。最终值能否对应历史 REST 行需单独验证。 |
| 标记价、指数价、资金费率等 | 各频道更新时间、修正/重复推送和 REST 对应关系 | 时间相同不能直接视为同一事件；无稳定来源键时用采集 ID。预测值与最终结算值分开。 |

每条规则需要记录官方章节、核对日期、原始脱敏样本、来源键作用域、快照/更新类型、重连行为、WS/REST 是否等价、测试向量和负责人；没有证据的跨源合并保持关闭。官方资料入口及核对表见 [OKX API 索引](okx-api-reference.md#每项功能编码前的核对记录)。

## 多节点采集所有权

按 `environment + product_id + channel + 订阅参数` 定义 feed，并核对内部产品到 OKX `instId` 的映射。初版用 PostgreSQL 中的 feed 所有权记录分配**单活发布者**：受限权限的 `ingest` 身份只能领取/续租采集权及读取代次，不能访问账户账本或交易密钥。取得新所有权会递增持久代次；每条事件带代次。失去租约、PG 不可用或续租状态不明的节点停止把该 feed 标记为可信并停止新发布。待命节点接管后重新订阅、建立快照/预热与序列可信状态，才恢复可信输出。

所有权代次只能阻止旧节点继续执行本地授权步骤，不能撤销其已排队或在网络途中的 Kafka 发布。下游保留旧代次记录以供审计，但在已观察到新代次后隔离迟到的旧代次事件；不能将其插回可信序列。切换窗口中的重复、缺口与顺序不确定性必须显式标记 feed 不可信并重建。来源有稳定身份时可识别被重复采集的同一事件；仅有采集 ID 时不能承诺跨节点去重。采集权状态、发布确认、代次切换和缺口原因分别持久/记录，不能以“租约已切换”推断 Kafka 中没有旧消息。

## 去重、版本与补数

消费者以 `event_id` 作幂等键，仍检查来源、产品、频道、schema、序列与时效。同一 ID 在同一 schema 版本的规范业务载荷必须一致；接收时间、来源会话、位点和归档位置不参与业务载荷比较。冲突事件隔离并停止相关进度。schema 变更后若仅表示形式改变，保留原事件 ID，并通过版本化迁移比较等价业务值；无法证明等价时拒绝合并。身份构造规则变更需新 `identity_rule_version`、旧新 ID 映射/迁移或隔离的新命名空间，不能让同一 ID 静默指向另一事件。

去重状态的保留窗口至少覆盖该消费者允许的 Kafka 重放和恢复窗口；窗口、容量与清理策略由保留期及负载测试冻结。长期归档回放不能依赖有限在线去重缓存：在独立回放命名空间重建状态，或使用可核验的持久事件索引。检查点记录处理范围、输出版本与去重状态水位；不能先推进位点再丢弃去重状态。超出可证明窗口时停止可信输出并重建，不能假定旧事件不会再到达。

REST 历史补数与 WS 实时事件保存各自来源及 `capture_id`。只有经逐频道验证两者粒度、来源键和修订语义一致，才可映射到同一个 `event_id`；否则保留两条事件，通过来源、时间范围和覆盖规则选择策略输入，不做价格/时间近似合并。补数不能抹去历史缺口或重新解释已提交交易决策；回放报告须标明补数来源与原始在线可见性。

## 验收与待冻结事项

协议测试覆盖同帧多事件、重复帧、重连重收、未收盘 K 线连续更新、盘口重建、同 ID 异载荷、不同 schema 等价迁移、WS/REST 不等价补数。多节点测试覆盖双节点竞争、租约过期、PG 不可用、旧发布者在新代次后送达、Kafka 确认丢失、崩溃后重收和去重窗口到期。验收必须分别报告“可跨源识别的事件”和“仅可重投递去重的采集记录”，不得合并成一个去重成功率。

首次编码前冻结：每个实际使用频道的来源键与作用域、ID 编码/哈希和版本、采集代次存储与权限、去重状态实现/保留窗口、补数覆盖规则、订阅切换后的可信恢复条件。没有这些证据的频道保持只读或不进入交易决策。

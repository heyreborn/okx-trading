# 性能与容量设计

状态：编码前设计草案。本文约束多产品、多策略、多机模拟盘的性能实现与验收；准确性、事实新鲜度、风险和可恢复性优先于吞吐。具体数值均为待冻结参数，由可重复的负载与故障试验确定，不把少量产品的首轮验证结果外推为容量承诺。模块边界见 [架构](architecture.md)，失败语义见 [实施协议](implementation-protocols.md)，运行指标归属见 [配置与观测规范](configuration-and-observability.md)。

## 链路与预算

分别测量：`OKX WS 接收 -> 校验/规范化 -> Kafka 发布确认 -> 消费/重排 -> 策略实例目标 -> 组合/风险 -> PG 批准与 outbox 提交 -> OKX 请求 -> 远端回报与对账`。记录各阶段排队和执行时间，以及端到端事件年龄；归档走独立消费链路，其积压不能直接占用交易关键路径，但缺失归档证据触发的门禁仍须遵守契约。OKX 网络与交易所处理时间单独报告，不能计入本机优化收益。

阶段耗时使用进程内单调时钟。跨节点端到端时间使用各节点校准后的 UTC 时间及其误差范围；交易所时间、接收时间、发布时间和决策时间分别保存，时钟失准时不得声称精确的跨节点延迟。事件年龄及输入可信度在做决策时重新检查，不能因为队列最终清空就把过期事件作为有效信号。

编码前按策略需要的新鲜度冻结端到端年龄上限、各阶段预算、积压恢复时限和稳态/突发容量目标；容量目标同时声明产品数、每产品 feed 数、每产品策略实例数、跨产品输入数、账户数和订单速率。每个队列给出条数、字节数、最老事件年龄及超限动作。预算之和应覆盖关键路径，但远端响应与私有回报使用独立预算，不能以降低安全校验来补偿外部延迟。

## 实现选择与成本

| 位置 | 首版实现约束 | 要验证的性能代价与正确性边界 |
| --- | --- | --- |
| Tokio 调度 | 长期任务由 supervisor 管理；按 feed、分区或实例复用工作任务，限制并发和队列容量。CPU 密集计算、压缩和同步阻塞工作进入有界执行池。 | 测任务调度等待、worker 占用和池队列峰值；不得为每条事件无界 `spawn` 或无界 `spawn_blocking`。饱和时按协议暂停/失信，不能静默丢弃。 |
| 行情解析与分发 | 原始帧只解析一次，规范化事件按订阅计划分发；同产品多策略共享 feed。按语义需要持有数据，确有多个拥有者时再使用共享缓冲。 | 量测每事件分配、复制、序列化次数和内存峰值；避免为每个策略重复解析 JSON。共享缓冲仍需限制持有时间及累计字节数。稳定 `event_id` 和发布确认不因优化改变。 |
| Kafka | 按稳定产品 key 保持分区顺序；发布采用有界批量和有限等待，并等待 Broker 确认。消费者按实例检查点恢复。 | 测批次大小/等待对 p99 和吞吐的影响、热点产品分区、lag 与恢复速度；不得靠提前确认、无确认发送或跳过重放提高指标。 |
| 策略与数值 | 每实例状态独立且有界；可用增量更新时，先证明其与完整计算在相同事件序列下等价。跨产品输入按确定性水位对齐。 | 测单事件计算、状态增长和策略数扩展。金融决策边界保持十进制强类型和显式舍入；若行情内部改用定标整数或紧凑表示，先证明范围、转换和极值一致；不得以 `f64` 承载订单金额或数量。 |
| PostgreSQL | 账户批准事务短而完整，事务内不调用 OKX；连接池有界，建立必要索引并以实际数据量检查查询计划。 | 测连接池等待、行锁等待、事务 p99、死锁和 WAL/磁盘增长。账户锁、唯一约束、预留和审计原子性不能为吞吐而移除；避免对每条无目标变化的行情开启批准事务。 |
| OKX REST/WS | 复用 HTTP 客户端和连接；限速、并发、超时预算分别约束查询、撤单和新开仓。 | 测请求排队、限速等待、未知提交及核对时延。不能对下单 POST 做通用重试，也不能让新单挤占恢复查询预算。 |
| 归档 | Parquet 编码与上传由独立 worker 有界批处理；以最大字节数和最长等待共同结束批次。 | 测编码 CPU/内存、对象写入、Kafka lag 和故障后的追赶时间。对象与清单持久化前不能提交消费进度。 |
| 观测 | 热路径日志按级别和字段预算控制；高基数 ID 放在日志/审计而非指标标签。 | 测日志量、指标开销及高负载下丢日志行为；交易审计和拒绝原因不能采样或因日志后端故障而丢失。 |

局部基准用于定位解析、数值、策略和编码热点；只有 profiling 指向瓶颈时才调整数据结构、分配或批量参数。优化后检查确定性回放、金额守恒、事件身份、风险门禁与故障恢复，不允许以更快的错误结果通过验收。

## 测量与试验

- 所有关键阶段记录 p50/p95/p99、吞吐量（事件数和字节数）、队列条数/字节数/最老年龄、Kafka 分区 lag、CPU、常驻内存及分配、PG 连接池/锁等待/事务时间、归档对象大小及写入时间。产品或策略实例维度可在负载报告中分析；在线指标标签仍遵守低基数规则。
- 用真实或脱敏、可重放的稳态与突发行情，覆盖 SPOT/SWAP 混合、同产品多个策略、跨产品输入、热点产品、WS 断线重连、Broker/PG 变慢及进程重启。分别测只读链路和经显式授权的模拟盘订单链路；两者结果不能混用。
- 单机 Compose 用于功能及初步基准；多机容量结论在目标网络、存储、复制拓扑上测。固定代码、`Cargo.lock`、配置、数据集和构建模式（release），记录硬件、容器资源限制、服务版本、分区数、预热时间、运行窗口与重复次数。比较变更前后的分位数和资源占用，并报告样本量、置信范围或运行间波动。
- 容量验收同时检查事件缺口/快进、过期输入拒绝、订单未知数、重复意图、预算守恒、回放一致性和故障追赶时间。任何正确性断言失败均使性能结果无效；达到稳态吞吐但队列持续增长也不算通过。

首轮阈值在实测前保持“待冻结”：最大产品/实例/账户规模、各类输入速率和突发长度、端到端年龄与阶段延迟、队列容量、Kafka 保留与分区、PG 池大小、Parquet 批次、恢复追赶时间，以及允许的 CPU/内存/磁盘余量。将冻结值连同环境和负载样本写入容量报告；变更关键路径、状态表示、分区策略或基础设施版本后重测受影响场景。验收分层见 [测试与验收策略](testing-strategy.md)。

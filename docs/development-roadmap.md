# Rust 功能开发任务总表

状态：持续更新。阶段 0 的 DEV-001 至 DEV-006 已完成；后续阶段任务尚未开始。顺序表示推荐交付路径；同阶段内无依赖的任务可调整，但不得越过阶段验收门禁。目标目录和依赖方向以 [架构文档](architecture.md)为准，技术选择以[技术决策](technology-decisions.md)为准。本表不授权自动交易或实盘交易。

## 使用规则

- 每个 `DEV-xxx` 是可单独验收、单独提交的最小计划任务。实际实施中若仍过大，可拆出连续子任务并保留原编号作为汇总；不要把多个无关任务塞进一个提交。提交规则见 [Git 规范](git-workflow.md)。
- 创建虚拟 workspace 时先建根配置和第一个需要实现的 package；其余目标目录随对应任务创建，并加入显式 `[workspace].members`。不为尚无实现的 package 制造空库或空白 README。
- 每个 package 的创建或修改须同步完成其 `README.md`、每个实际 module 的 `//!`、公开 API rustdoc、相应 Rust 测试及受影响的专题文档，按[模块文档规范](module-documentation.md)执行。下面的“完成”均包含这一共同要求。
- 编码前核对 Python 的实际行为和测试，记录“行为证据 -> Rust 模块/契约 -> Rust 验收测试”；Python 只作功能参考，不搬运代码。涉及 OKX 的任务还须按 [OKX 官方 API 依据](okx-api-reference.md#每项功能编码前的核对记录)重新打开相应官方章节和变更日志，记录查询日期、账户模式、权限、字段单位、限速和模拟盘差异。
- 任务完成时把 `[ ]` 改为 `[x]`，在该项后附提交 ID、验证命令或报告位置及仍未验证的场景。通过单元/假服务测试不等于通过真实 PostgreSQL、Kafka、对象存储或 OKX 模拟盘验收。

- [ ] **DEV-045 · 账户内核验收 C**｜`integration-tests`。在真实 PG/Kafka 下验证绝对目标、组合冲突、预留、共享成交归属、两种持仓模式和双副本接管。完成：达到[测试矩阵 C](testing-strategy.md#功能验收矩阵)，发送链路仍保持关闭。

## 阶段 5：显式模拟盘执行（验收 D/E）

- [ ] **DEV-048 · 回报核验与入账**｜`apps/trader/usecases::settlement`。正常回报直接核验入账，冲突或未知事实经 `reconciliation` 核对，再同事务保存状态、成交归属、费用、预留和审计。完成：私有 WS/REST 乱序、重复成交及日志故障下账本可恢复测试。
- [ ] **DEV-049 · 手动现货模拟盘验收 D**｜`apps/trader/runner`、`integration-tests`。实现必须显式触发、限定最小量的现货探针；至少两个现货、各两个策略，核对成交、费用、撤单、未知结果和重启。完成：达到[测试矩阵 D](testing-strategy.md#功能验收矩阵)，现货自动执行仍关闭。
- [ ] **DEV-050 · 手动永续模拟盘验收 E**｜`apps/trader/runner`、`integration-tests`。至少两个不同规格永续、各两个策略，分账户模式验证逐仓、双侧开平、费用、资金费与重启核对。完成：达到[测试矩阵 E](testing-strategy.md#功能验收矩阵)，未出现的真实样本明确标未验证。

## 持续核对

阶段验收 A-F 的完整判据在[测试策略](testing-strategy.md#功能验收矩阵)。每次开始任务前查看其前置能力是否有实际代码、测试与提交证据；上表顺序不能替代依赖核对。每次完成任务后更新该项状态和报告，再按[Git 规范](git-workflow.md)提交。涉及交易所协议、身份规则、精度、事务或接管的变更必须同时复核[OKX 官方依据](okx-api-reference.md)、[实施协议](implementation-protocols.md)及[故障恢复](failure-and-recovery.md)。

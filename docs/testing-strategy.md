# 测试与验收策略

状态：设计草案。测试目标是证明 Rust 系统的契约、恢复与交易准入，不要求与任何既有实现逐行相同。每个验收结论必须指出环境、版本、产品/账户模式、样本、失败记录和仍未覆盖的场景。依据见 [契约与不变量](contracts-and-invariants.md)、[实施协议](implementation-protocols.md)、[配置与观测规范](configuration-and-observability.md)及 [故障边界与恢复](failure-and-recovery.md)。

实现或修改 package/module 时，文档与测试一起进入交付范围：按 [模块文档规范](module-documentation.md)更新 package `README.md`、module rustdoc 和适用的跨模块协议文档，并检查文档所列的边界场景有对应验证。

## Python 功能参考与验收

在实现每项能力前，核对 [Python 迁移交接文档](../../okx-trading-py/docs/rust-migration-guide.md)中对应的源码、测试和验收状态，记录功能、输入输出、边界条件、失败行为及证据位置，再映射到 [Rust 架构](architecture.md)中的唯一所有者和 Rust 测试。区分已上线观察链路、手动模拟盘探针、仅通过离线测试的逻辑和未实现功能；不能把探针结果当成自动交易准入。对旧行为有意改变时记录原因、新契约及相应测试。

所有新增测试与实现使用 Rust。Python 样本可用于构造脱敏、版本化的输入夹具和预期业务不变量；Rust 测试应按自身契约断言身份、精度、状态、事务和恢复结果，而非复制 Python 测试代码或只比较两边输出。OKX 协议字段、权限和限速以官方文档及模拟盘验证确认；交易安全相关差异须在对应验收阶段解决。

## 测试层级

| 层级 | 位置与工具 | 必须覆盖的行为 |
| --- | --- | --- |
| 单元与表驱动测试 | 所属 module 的 `#[cfg(test)]`，`cargo test`/Nextest | 配置未知字段/重复 ID/来源冲突、产品/策略强类型 ID、绑定关系与能力、单位、取整、净/毛敞口、两种持仓模式、订单状态机、拒绝原因。 |
| 性质测试 | 领域 package，`proptest` | 输入顺序变化不改确定性合并；份额/费用守恒；预留不超预算；累计成交单调；重放幂等。 |
| 协议测试 | `okx-client`、`market-bus`、`archive` 各自的 `tests/`；可控 HTTP/WS 假服务 | 签名、限速、非法字段、WS 断线/乱序、逐频道 ID 与更新语义、冲突隔离、未知 POST、Broker 发布确认、对象写入中断。 |
| 跨包集成测试 | `integration-tests` 独立 package；由 Docker Compose 启动隔离 PG/Kafka/S3 兼容服务 | 真实事务与锁、采集发布权竞争/代次、消费者重平衡、归档提交顺序、账户双副本竞争和接管。 |
| 进程级测试 | 三个 `apps/<role>/runner/tests/` 及单 package 应用的 `tests/` 启动对应 binary | 启停、缺凭据、环境变量越权覆盖、配置版本分歧、信号处理、健康接口、无权限进程隔离、JSON 日志脱敏及指标标签基数。 |
| 故障演练 | 隔离的多节点部署 | PG 主从切换、Broker/对象存储不可用、网络分区、旧执行者恢复、备份恢复。 |
| OKX 模拟盘验收 | 单独的显式运行任务，需模拟盘凭据 | 真实账户设置、订单、成交、费用、撤单、资金费及重启远端核对。 |

性质测试重点生成边界值和失败序列，不仅生成正常行情。对交易金额、合约面值、步长、负数/零、极大与极小小数进行往返和溢出测试。每个发现的失败输入留作回归样本。测试代码不存真实密钥、完整账户响应或可提交实盘的配置。

## 自动化门禁

每个变更执行 `cargo fmt --check`、`cargo check --workspace --all-targets`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo nextest run --workspace`、`cargo test --workspace --doc`、`cargo deny check` 和 `cargo doc --workspace --no-deps`。Nextest 不运行 doctest，故单列文档测试。执行前在 workspace 目录直接检查本机 `rustc`、`cargo` 及所需子命令；版本兼容则直接运行，不加 `mise exec`。直接命令找不到时才检查 Mise 安装与 shell 激活；仍不可用时使用固定 builder 容器。CI 使用提交的 `Cargo.lock` 与固定工具链版本；外部服务集成测试由 Compose 启动隔离实例，不能连接交易用 Kafka topic、PG 库或 OKX 凭据。PG、Kafka、对象存储不在宿主机原生安装；部署约定见 [Docker Compose 文档](compose-deployment.md)。

较慢的跨进程、负载和故障演练可在独立 CI 阶段或定期任务运行，但凡修改订单、账户、消息身份、数据库迁移或接管流程，相关真实基础设施测试是合并门禁。只通过 mock 测试不能证明事务或多机接管正确。

配置或审计协议变更还需验证多节点滚动发布/回滚、决策引用的版本不变、审计与账本同事务提交/回滚，以及日志采集故障时仍可从权威事实恢复。

行情身份规则变更需按 [行情事件身份与采集接管](market-event-identity.md)重跑逐频道样本：同帧多事件、重复帧、重连、未收盘 K 线连续更新、快照/增量、身份版本迁移、WS/REST 补数映射、去重窗口到期和旧采集者迟到发布。测试报告区分跨源确定性去重与单次采集记录重投递去重。

产品与策略关系变更需按 [产品与策略身份及绑定](product-strategy-model.md)验证：同产品多类型/多实例、同类型多实例、跨产品输入/多目标、跨账户隔离、未知产品类型与账户许可失效、产品规格更新、停用实例后的库存/订单追溯、不兼容状态迁移及回放版本固定。

目标与组合政策变更需按 [策略目标与实例执行协议](strategy-target-and-execution.md)验证：`Target(0)`/`NoSignal`/`Unavailable`、过期及取代、同产品反向调整、预算不足拒绝、同向订单的部分成交/费用分摊、目标 ID 重投递、旧观察者迟到、状态 schema 迁移和账户产品门禁。真实 PG 测试覆盖状态/目标 outbox/检查点原子提交及两观察者代次竞争。

按 [端到端职责与交接](architecture.md#端到端职责与交接)验证模块边界：OKX 适配器的有类型输出交给行情规则；策略只产生实例目标；目标 outbox 重复交付、旧代次和过期目标均不能生成第二笔批准；组合冲突与风险额度分别返回原因；批准用例在账户锁内复核并提交；发送用例只处理已提交订单 outbox；订单状态与成交归属计算在同一入账事务中落盘。真实 PG 并发测试必须证明事务外预计算的候选在事实、目标或配置版本变化后不能沿用旧风险结果提交。分别注入正常私有回报、HTTP 接受但未成交、POST 结果未知、REST 补查及回报逆序，验证核对用例只处理未知/冲突事实，正常回报可独立入账；归档消费积压不占用订单关键路径。

## 功能验收矩阵

| 阶段 | 要证明的能力 | 未通过时的限制 |
| --- | --- | --- |
| A. 契约与只读目录 | 内部产品/OKX 产品映射、SPOT/线性 SWAP 类型、策略类型/实例/绑定、账户产品许可和两种账户模式识别；错误单位与过期事实被拒绝。 | 只有离线计算和只读检查。 |
| B. 行情与回放 | 多机采集单活发布权、观察实例单活、Kafka 发布确认、逐频道身份、状态/目标检查点、归档、缺口检测及相同输入的在线/回放目标一致。 | 不生成可执行订单意图。 |
| C. 账户内核 | 真实 PG/Kafka 下，绝对目标组合与冲突拒绝、多产品并发预留、共享订单归属、双侧风险、重复事件和故障接管均正确。 | 执行者保持只读。 |
| D. 手动现货模拟盘 | 至少两个现货、各至少两个策略；显式最小量探针完成成交、费用、撤单、未知结果和重启核对。 | 现货自动执行关闭。 |
| E. 手动永续模拟盘 | 至少两个不同规格的 USDT 本位永续、各至少两个策略；净仓和双向模式分别验证开减平、侧别、保证金、成交费用和资金费。 | 对应模式的永续自动执行关闭。 |
| F. 混合与持续运行 | 现货/永续同账户并发候选不超额；产品故障隔离、账户故障全局暂停、跨节点接管、备份恢复及容量测试。 | 混合自动执行关闭。 |

自动交易按产品类别和持仓模式分别授权；一个阶段通过不自动打开后续阶段。真实部分成交后撤单、同合约真实双侧持仓或资金费样本若未出现，报告明确标为未验证，不能用假服务样本冒充现场验收。策略准入还要有单独的收益与成本证据；技术正确不等于策略可获利。所有自动执行开关初始为关闭，实盘不设开关。

## 多机与容量试验

在至少两个采集/观察节点、两个 trader 副本、跨节点 PG/Kafka/对象存储的隔离环境运行故障矩阵。注入重复投递、消息乱序、采集所有权切换后旧代次发布、发布确认未知后崩溃、消费者重平衡、去重状态过期、队列满、进程强制退出、PG 主库切换、网络分区、HTTP 提交超时、私有 WS 断开、执行租约过期及旧执行者恢复。每个用例断言：暂停范围正确、同一决策不产生第二个可提交意图、额度不超额、未核清订单不重发、恢复后远端与本地账本一致。

容量试验使用可重复的真实或脱敏行情突发窗口，并同时运行采集、Broker、观察、归档和账户只读评估。记录输入速率、端到端事件年龄及各阶段 p50/p95/p99、丢弃/快进、队列峰值与最老年龄、分区积压、PG 连接池/锁等待/事务时延、对象写入时延、CPU/内存和磁盘增长。测试包含同产品多策略、热点产品及故障后的追赶；队列持续增长或任一正确性断言失败均不通过。产品上限与阈值由该试验设定，数据集、拓扑、版本和运行间波动随报告保存；离线纯函数吞吐不能作为多机容量承诺。场景、指标与待冻结预算见 [性能与容量设计](performance-and-capacity.md)。

## 测试数据与报告

测试夹具按 schema 版本保存脱敏的市场事件、目录规格、账户模式、仓位、订单/成交回报和预期拒绝原因。时间、随机数、网络错误及任务调度在单元/协议测试中可控；多机测试另验证真实调度竞争。每份验收报告至少列出代码版本、依赖锁文件、环境拓扑、OKX 模拟盘账户模式、运行窗口、产品/策略集合、通过与跳过用例、未清订单和数据缺口。失败记录保留到修复并回归通过。

测试工具入口：[Cargo 测试布局](https://doc.rust-lang.org/cargo/guide/project-layout.html)、[Nextest](https://www.nexte.st/)、[proptest](https://docs.rs/proptest/latest/proptest/)、[Clippy](https://doc.rust-lang.org/clippy/usage.html)、[cargo-deny](https://embarkstudios.github.io/cargo-deny/checks/index.html)。

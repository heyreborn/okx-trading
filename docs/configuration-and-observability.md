# 配置、环境与观测规范

状态：部署环境解析和观测基座已实现，业务 TOML 与进程接线仍待实现。本文定义多机运行时配置和观测的责任边界。`crates/config::deployment` 已冻结首批环境变量和密钥文件引用；`crates/telemetry` 已提供固定字段 JSON 日志、枚举化指标和进程健康类型。`config/env.example` 是非敏感模板，不是可运行的业务配置。架构归属见 [架构与功能归属](architecture.md)。

## 配置来源与优先级

| 来源 | 内容 | 规则 |
| --- | --- | --- |
| 版本化 TOML | 产品白名单及 ID 映射、策略类型/实例、输入与目标产品绑定、账户产品许可、策略参数、预算、风险政策、数据时效、交易准入门禁 | 每次发布有不可变版本与内容摘要；自动交易初始关闭。未知字段、重复 ID、悬空或不兼容绑定、矛盾模式及越界数值拒绝启动/发布。 |
| 进程环境 | 配置文件位置、节点/进程身份、PG/Kafka/对象存储地址、日志过滤级别、密钥引用 | 只影响部署接线和观测；不能覆盖产品、策略、风险预算或交易门禁。每个进程只要求其角色需要的连接与凭据。 |
| 密钥供应 | OKX API 凭据、数据库/队列/对象存储凭据 | 由部署平台注入或通过引用读取，不写入 TOML、日志、错误链、测试夹具或镜像。生产不依赖本地 `.env` 文件。 |
| OKX 远端事实 | 产品规格、账户模式、费率、余额、仓位、订单与成交 | 配置不能覆盖远端事实；版本不匹配或事实过期时拒绝产生可提交意图。 |

`crates/config` 负责严格反序列化、字段范围、跨字段校验、规范化摘要与已解析版本类型；`config::deployment` 解析环境接线和密钥引用。`apps/*` 在启动时按角色加载配置、解析密钥、验证服务连接，再组装依赖。`ingest` 为 feed 发布权领取使用仅能访问对应 PG 租约记录的凭据，不持有账户账本或交易密钥。业务模块只接收经校验的不可变配置值及其版本，不直接读取环境变量或文件。远端目录/账户事实由所属适配器获取并由领域规则验证。配置加载错误应指出字段路径和原因，但不能输出密钥值。

配置中明确区分 `product_id` 与 OKX `instId`、`strategy_type_id` 与 `strategy_instance_id`。实例分别声明输入 feed 和目标产品，绑定有独立版本；同产品多实例、同类型多实例及跨产品输入均合法，但必须通过能力、账户和产品许可校验。产品或策略绑定变更不得静默搬移实例库存、未结订单或预算。完整模型见 [产品与策略身份及绑定](product-strategy-model.md)。

每个策略类型声明目标有效期和状态 schema 的允许范围；账户/产品配置声明组合政策与本地交易门禁。初版组合政策为 `RejectConflicts`，预算不足拒绝新批准。账户产品配置不覆盖 OKX 实际账户模式、保证金/杠杆或产品规格，发布和接管时重新核验。目标与实例代次的执行契约见 [策略目标与实例执行协议](strategy-target-and-execution.md)。

覆盖规则只允许部署参数有明确的环境覆盖来源；业务 TOML 不接受同名环境变量隐式覆盖。配置发布通过静态校验、只读差异检查和审批流程后形成不可变版本；节点启动时核对内容摘要。观察进程可在检查点边界切换版本，交易进程在账户安全边界切换；同一决策记录策略、产品规格和风险政策版本。集群版本不一致时停止受影响的新开仓并告警，不靠各机自行选择最新文件。回滚是发布一个明确的旧版本引用，不改写历史决策。

本机验证用 [Docker Compose](compose-deployment.md)启动 PG、Kafka、对象存储和应用；`config/env.example` 只作为非敏感部署变量模板。未跟踪的 `.env` 仅用于开发启动器/Compose 变量替换，不存真实密钥；应用配置逻辑只看到已注入的进程环境。密钥按容器角色单独注入，来源文件或环境由部署者保护；仓库忽略 `.env`、本地密钥、生成日志和运行数据。容器间地址使用服务名，不使用宿主机的 `localhost`。模拟盘/实盘环境是强约束：首版只允许模拟盘，端点、凭据环境及模拟盘请求头必须一致；没有通过环境变量打开实盘的后门。

## 日志、指标与追踪

`crates/telemetry` 为各进程初始化 `tracing`/`tracing-subscriber`，输出 JSON 到标准输出，由部署平台采集、集中存储和检索。默认记录 `timestamp`、`level`、`service`、`instance_id`、`environment`、`config_version`、事件名称与稳定原因码；相关用例附加 `account_id`、`product_id`、`strategy_instance_id`、`event_id`、`decision_id`、`clOrdId`、所有权代次等适用字段。跨进程上下文通过消息契约中的 ID 传播；不假设一次内存 span 能覆盖 Kafka、PG 与 OKX。

日志字段采用允许列表。不得记录 API key、secret、passphrase、签名头、数据库密码、完整 HTTP/WS 请求体、完整账户响应或原始个人信息；错误链也要脱敏。OKX 原始响应如需排障，使用受控短期存储及访问审计，不进入常规日志。日志过滤级别可由部署环境调节，但调高详细度仍受相同脱敏约束。日志写入失败由平台监控发现；本地日志不是交易恢复的事实来源。

指标覆盖 feed 新鲜度/缺口、Kafka lag、有界队列水位、WS 重连、HTTP 限速/错误、PG 事务时延、outbox 未知数、账户暂停原因、配置版本分歧、告警投递失败。指标标签只用服务、角色、环境、产品类别、原因码等受控低基数字段；订单 ID、决策 ID、策略实例 ID、账户 ID 不作全局时序标签。高基数查询使用日志和审计记录。readiness 表示当前角色所需依赖和事实可信度；liveness 仅用于进程重启判断，均不能自动解除交易暂停。

## 审计与告警

交易审计事实由 `trader_usecases::audit` 定义，配置发布和人工操作的审计事实由 `apps/admin` 定义；`persistence` 在有关业务事务中持久化：配置发布/回退、权限操作、决策输入版本、风险批准/拒绝、订单意图、远端确认、成交归属及人工干预。需要和订单状态原子提交的审计事实进入同一 PG 事务；跨系统结果通过 outbox/核对补记，不伪称跨系统原子性。审计采用稳定 ID、时间、操作者或自动决策来源、前后版本和结果；保留期、访问权限与备份按部署政策确定。

`ingest_usecases`、`observe_usecases`、`trader_usecases` 各自的 health module 产生所属范围的暂停原因和告警事件；`apps/notifier` 的投递 module 管理去重、重试、确认和渠道接线。日志级别不能替代告警严重度，告警投递故障由独立监控发现。服务恢复后，解除暂停需通过对应事实核验和明确的状态转换。

## 实施与验收

先冻结配置 schema、环境变量清单及密钥注入接口，再创建可运行 `config/example.toml` 和各应用启动入口。测试至少覆盖未知字段、重复策略实例、悬空/跨账户/不兼容绑定、产品 ID 与 OKX 标识映射冲突、缺失角色凭据、环境变量试图覆盖交易门禁、模拟盘环境混用、版本摘要不一致、滚动发布/回滚、日志脱敏、指标标签基数、审计事务回滚及日志系统不可用时的账本恢复。具体测试分层见 [测试与验收策略](testing-strategy.md)。
